# Mezgeb Specification (draft outline)

Status: DRAFT. Each section is an outline to be filled in before the code it
governs is written. A section is "done" when it states rules precisely enough
that two people would implement them the same way.

---

## 0. Purpose and scope

- An open-source, double-entry financial ledger in Rust on PostgreSQL.
- First-class **offline sync**: devices spend escrowed funds while
  disconnected and settle later, safely and deterministically.
- **In scope:** accounts, transfers, balances, holds, offline escrow and
  settlement, audit, history.
- **Out of scope:** users, KYC, cards, QR, fees policy, FX rates, UI. Those
  belong to the client application (e.g. Atronsa).
- Non-goals: being a general-purpose database; multi-region consensus (v1).

## 1. Glossary

Account, ledger (asset/currency partition), transfer, batch, posting,
pending, post, void, hold, escrow, voucher, receipt, device, counter, sync,
settlement, event time, recorded time, daily close, invariant,
ledger receipt (signed proof that the ledger committed a transfer; see §7.2).

## 2. Invariants (the contract — everything else serves these)

Each invariant gets an ID, a precise statement, where it is enforced
(core / database / both), and how it is tested.

- INV-1 Every transfer debits exactly one account and credits exactly one
  account for the same positive amount.
- INV-2 Sum of all debits == sum of all credits, per ledger, at all times.
- INV-3 Transfers are immutable once recorded; corrections are new transfers.
- INV-4 A transfer ID is applied at most once (idempotency).
- INV-5 Account balance flags (e.g. debits must not exceed credits) hold after
  every committed batch.
- INV-6 Transfers only move value between accounts on the same ledger.
- INV-7 A pending transfer resolves at most once (post XOR void XOR expire).
- INV-8 Replaying the journal from empty reproduces every balance exactly.
- INV-9 An offline device can never settle more than its reserved amount.
- INV-10 A (device, counter) pair settles at most once.
- INV-11 Two different receipts with the same (device, counter) are never both
  settled, and always raise a conflict.
- INV-12 Closed periods are never modified.
- INV-13 Every committed transfer has exactly one ledger receipt. Its
  signature verifies against the ledger key that was active at its
  `recorded_time`, and retrying the same transfer returns the identical
  receipt bytes.

## 3. Data model

### 3.1 Identifiers
- 128-bit IDs, generated by the client (UUIDv7 recommended for time order).
- Why client-generated: makes retries and offline creation idempotent.

### 3.2 Amounts
- Signed 64-bit integer minor units (e.g. santim). Amount must be > 0.
- No floats, no decimals in the core. Overflow is an error, never a wrap.

### 3.3 Ledger (asset partition)
- `ledger: u32` identifies a currency or asset. No cross-ledger transfers;
  currency exchange is modelled as two linked transfers via a liquidity
  account.

### 3.4 Account
- Fields: id, ledger, code (category), flags, debits_pending,
  debits_posted, credits_pending, credits_posted, user_data, created_at.
- Flags: DEBITS_MUST_NOT_EXCEED_CREDITS, CREDITS_MUST_NOT_EXCEED_DEBITS,
  CLOSED, HISTORY (keep balance snapshots).
- Accounting type (asset/liability/equity/revenue/expense) lives in `code`
  and the client's chart of accounts; the core only enforces flags.

### 3.5 Transfer
- Fields: id, debit_account_id, credit_account_id, amount, ledger, code,
  flags, pending_id, timeout, user_data, event_time, recorded_time.
- Flags: LINKED, PENDING, POST_PENDING, VOID_PENDING, BALANCING_DEBIT,
  BALANCING_CREDIT.

### 3.6 Time
- `recorded_time`: assigned by the ledger, strictly monotonic. Authoritative.
- `event_time`: claimed by the client/device. Informational, bounded and
  validated, never used for ordering.

## 4. Transfer semantics

- 4.1 Validation order and the exact error for each failure.
- 4.2 Single posted transfer.
- 4.3 Two-phase: pending → post (full or partial) / void / timeout expiry.
- 4.4 Linked transfers: a chain succeeds or fails as one.
- 4.5 Balancing transfers (transfer "up to" an amount).
- 4.6 Batches: ordering, atomicity, result per item.
- 4.7 Idempotency: same ID + same body → original result;
  same ID + different body → `exists_with_different_fields` error.

## 5. Offline sync

### 5.1 Threat model
Cloned device, replayed receipt, forged receipt, device that never syncs,
wrong/hostile clock, payer–merchant collusion, lost device, partial sync,
merchant uploads receipt twice, payer and payee upload the same receipt.

### 5.2 Device trust tiers
- Tier A: secure element (card). Tier B: hardware keystore (StrongBox/TEE).
  Tier C: software keys. Each tier has its own offline limit and expiry.

### 5.3 Voucher (offline allowance)
- Issued online. Creates a pending/escrow transfer from the user's account to
  an `offline_reserved` account bound to one device.
- Contents: voucher_id, device_id, account_id, ledger, amount, counter_start,
  expires_at, issuer signature.

### 5.4 Receipt
- Contents: device_id, voucher_id, counter, prev_receipt_hash, payee account,
  amount, event_time, payer device signature, optional payee ack signature.
- Hash chain per device: each receipt commits to the previous one.

### 5.5 Ingestion and settlement rules
- Outcomes: SETTLED, DUPLICATE, WAITING_FOR_GAP, CONFLICT, EXPIRED,
  OVER_LIMIT, BAD_SIGNATURE, UNKNOWN_DEVICE.
- Either party may upload; the result is identical regardless of who or when.
- Gap handling: how long to wait, what is settled meanwhile.
- Conflict handling: freeze device, settle nothing further, raise alert.

### 5.6 Voucher end-of-life
- Expiry, top-up, revocation, return of unspent escrow, late receipts after
  return (who absorbs the loss — policy hook for the client).

### 5.7 v1 rule
- Funds received offline are not spendable offline until synced
  (chain depth = 1).

## 6. Periods and daily close

- Close a period: freeze balances, compute and sign a journal hash.
- Late-arriving offline receipts post into the current open period with a
  reference to their event_time.

## 7. Audit and tamper evidence

### 7.1 Journal integrity
- Hash chain over the transfer journal.
- Signed checkpoints at each close; verification tool.
- Database role permissions: no UPDATE/DELETE on journal tables.

### 7.2 Ledger receipts (signed proof for every transfer)

Offline payments already carry device-signed receipts (§5.4). Ledger receipts
extend signed proof to **every** committed transfer, online or offline: the
ledger signs what it recorded, and the client keeps a copy it can verify
without trusting the database. Accounting stays double-entry; the receipt is
evidence, not a third ledger column.

- **When issued:** for every committed transfer: posted, pending, post,
  void, expiry, and settlement of an offline receipt. Failed transfers get no
  receipt.
- **Contents:** receipt format version, the transfer's canonical fields
  (§3.5), `recorded_time`, the transfer's journal hash and `prev_hash`
  (§7.1), the signing key ID, and the signature.
- **Signature:** over a canonical, versioned byte encoding of the contents.
  Algorithm provisionally Ed25519; the algorithm and the encoding are decided
  in an ADR and are part of the public API once frozen.
- **Delivery:** returned with each successful item from `create_transfers`,
  and retrievable later by transfer ID.
- **Idempotency:** the receipt is stored with the transfer when the batch
  commits. A retry with the same ID and body returns the stored receipt, never
  a newly signed one (INV-13).
- **Purity:** `mezgeb-core` stays free of keys and I/O. It returns the
  canonical bytes to sign; signing happens in the server/storage layer inside
  the same database transaction.
- **What it proves:** the ledger committed exactly this transfer at this
  position in the journal. Combined with a signed checkpoint (§7.1), anyone
  holding receipts can detect a journal that was rewritten or had entries
  removed.
- **What it does not prove:** that the account holder authorised the
  transfer. That needs client-signed requests (see §14).
- **Verification:** a standalone verifier (CLI and library) checks receipt
  signatures, key validity at `recorded_time`, and chain links against a
  checkpoint.

## 8. Storage (PostgreSQL)

- Schema, indexes, partitioning (transfers by month).
- Isolation level and lock ordering; deadlock avoidance.
- Hot accounts: contention strategy.
- Constraints and triggers as a second line of defence for INV-1..INV-7.
- Migrations policy: forward-only, reviewed, tested on a copy of real data.

## 9. API

- gRPC (see `proto/mezgeb.proto`): create_accounts, create_transfers,
  lookup_accounts, lookup_transfers, get_account_history, issue_voucher,
  ingest_receipts, close_period.
- Batch-first: every write takes a list.
- Every successful transfer result includes its ledger receipt (§7.2).
- Errors: stable, enumerated codes.
- Versioning and backward-compatibility policy.

## 10. Testing and verification

- Unit and property-based tests for every invariant.
- Deterministic simulator (`mezgeb-sim`): seeded, reproducible; injects
  crashes, retries, reordering, duplicate and delayed sync, cloned devices,
  clock skew. Checks all invariants after every step.
- Replay test: rebuild balances from journal and compare.
- Shadow mode: run beside an existing ledger and compare nightly.

## 11. Performance targets

- Transfers/second (single node), p99 latency, hot-account throughput.
- Benchmark harness and reference hardware.

## 12. Operations

- Backups and point-in-time recovery, monitoring, alerts on invariant
  breaches, key management for voucher signing, disaster recovery.

## 13. Security

- Key hierarchy (issuer keys, receipt-signing keys, device keys), rotation,
  revocation list. Retired receipt keys stay published so old receipts remain
  verifiable.
- Authentication between client apps and the ledger.

## 14. Open questions

- Regulator requirements for offline stored value (limits, expiry, reporting).
- Who bears loss for late receipts after voucher return?
- Partial settlement when a gap never fills?
- Multi-currency in v1 or later?
- Client-signed transfer requests (proof of authorisation): v1 or later, and
  is the signature stored with the transfer?
- Receipt-signing keys in an HSM/KMS, or in process for v1?
