# Architecture Decision Records

[Documentation](../README.md) · Source: [architecture](../architecture.md) · Step: [1.02](../roadmap/phase-1-core-engine/02-architecture-decisions.md)

An Architecture Decision Record (ADR) is a short document that records one
decision about how Mezgeb is built: the problem, the options that were
considered, the choice and what it costs. Decisions are recorded so they are
not re-argued every month, and so that any table, crate or rule can be traced
back to the reason it exists.

## Statuses

| Status | Meaning |
|---|---|
| Proposed | Written and under discussion. Not yet binding. |
| Accepted | Binding. Code and docs must follow it. |
| Superseded by NNNN | Replaced by a later ADR. Kept for history, never deleted. |

An accepted ADR is not edited to change its decision. To change a decision,
write a new ADR that supersedes it, and set the old one's status to
*Superseded by NNNN*. Typos, links and an *Evidence* section added later (for
example, measurements in step 1.10) are fine to edit in place.

## Review checklist

Every ADR must pass this before it is accepted:

- [ ] The context states the problem without assuming the answer.
- [ ] The decision is one clear, testable statement.
- [ ] At least two alternatives are listed, each with reasons for and against.
- [ ] Consequences include the costs, not only the benefits.
- [ ] It names the roadmap steps that implement or test it.
- [ ] It names any part of the spec or code it makes out of date.

## Template

Files are named `NNNN-short-kebab-title.md`. Numbers are never reused.

```markdown
# NNNN. <Decision as a short statement>

| | |
|---|---|
| Status | Proposed |

| Answers | <architecture section> |
| Implemented in | <roadmap steps> |

## Context

<The problem and the forces at play. Why a decision is needed now.>

## Decision

<What we will do, in one or two short paragraphs.>

## Alternatives considered

| Option | For | Against |
|---|---|---|
| **<Chosen option>** | | |
| <Alternative> | | |

## Consequences

**Positive:** <what gets easier or safer>

**Negative:** <what it costs, and how that cost is contained>

**Makes out of date:** <spec sections or code that must change>
```
