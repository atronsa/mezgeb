## How a posting works

In one transaction:

1. Lock every account the entry touches, `SELECT … FOR UPDATE` in ascending
   ID order (ADR-0007).
2. Validate with `mezgeb_core::validate` against those locked rows, so the
   balances it checks cannot change before commit.
3. Insert the entry.
4. Apply the entry's net effect to each account, one `UPDATE … RETURNING`
   per account, and work out each line's totals after it from the totals the
   database returns.
5. Insert every line in one statement (`UNNEST`).
6. Commit. The database checks the result again (docs/db-schema.md).

**Differences from the step's task list:**

- `post_entry` takes an `EntryDraft`, not a `BalancedEntry`, and validates it
  once, inside the transaction, against the locked rows. A `BalancedEntry`
  built before the locks were taken would have been checked against
  balances that may since have changed; validating under the lock is the
  stronger guarantee.
- Compile-time checked queries (`query!`, with offline data for CI) and
  `tracing` are not used yet. They add a build step for every contributor;
  they are revisited when the API is built (step 2.07).

## A bug the differential test found

On its first run, the differential test failed and shrank the failure to two
operations:

```
step 1, Transfer { debit: 4, credit: 4, amount: 1 }
  oracle:     Ok(Posted(…))
  postgresql: Err(Storage("… violates check constraint \"accounts_not_negative\""))
minimal sequence: [Open(4), Transfer { debit: 4, credit: 4, amount: 1 }]
```

An entry that debits and credits account 3010 (equity) by the same amount
nets to zero and is valid. The first version of the engine updated totals
line by line, so after the debit line the account was briefly negative, and
PostgreSQL checks a `CHECK` constraint after every row update, not at commit.
The engine now applies each account's net effect in one update. Regression
tests were added on both ledgers (`the_same_account_on_both_sides_posts`).

## Exit gate

**Gate:** killing the test process mid-run never leaves an entry without
lines, verified by the integrity query after a forced abort.

`crash_writer write` posts three-line entries (Dr bank, Cr wallet, Cr fee
revenue) continuously. It was killed with `SIGKILL` five times after a
random 2–6 seconds, and `crash_writer check` ran the integrity queries after
each kill:

```
round 1: killed after 5s (exit 137)
126 entries; IntegrityReport { entries_without_lines: 0, unbalanced_entries: 0, accounts_with_wrong_totals: 0, unbalanced_currencies: 0 }
round 2: killed after 2s (exit 137)
190 entries; IntegrityReport { entries_without_lines: 0, unbalanced_entries: 0, accounts_with_wrong_totals: 0, unbalanced_currencies: 0 }
round 3: killed after 2s (exit 137)
254 entries; IntegrityReport { entries_without_lines: 0, unbalanced_entries: 0, accounts_with_wrong_totals: 0, unbalanced_currencies: 0 }
round 4: killed after 4s (exit 137)
356 entries; IntegrityReport { entries_without_lines: 0, unbalanced_entries: 0, accounts_with_wrong_totals: 0, unbalanced_currencies: 0 }
round 5: killed after 4s (exit 137)
475 entries; IntegrityReport { entries_without_lines: 0, unbalanced_entries: 0, accounts_with_wrong_totals: 0, unbalanced_currencies: 0 }
```

The PostgreSQL log confirms that two of the kills landed inside an open
posting transaction, which PostgreSQL rolled back:

```
LOG:  unexpected EOF on client connection with an open transaction
LOG:  unexpected EOF on client connection with an open transaction
```

**Result: passed.** No kill left an entry without lines, an unbalanced
entry or a wrong account total.
