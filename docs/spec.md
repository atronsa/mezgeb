# Mezgeb Specification (draft outline)

Status: DRAFT. Each section is an outline to be filled in before the code it
governs is written. A section is "done" when it states rules precisely enough
that two people would implement them the same way.

---

## 0. Purpose and scope

- An open-source, double-entry financial ledger in Rust on PostgreSQL.
- First-class **offline sync**: devices spend escrowed funds while
  disconnected and settle later, safely and deterministically.
- **In scope:** accounts, journal entries, balances, holds, offline escrow and
  settlement, audit, history.
- **Out of scope:** users, KYC, cards, QR, fees policy, FX rates, UI. Those
  belong to the client application.
- Non-goals: being a general-purpose database; multi-region consensus (v1).

## 1. Glossary

Account, chart of accounts, control account, sub-account, journal entry,
line, side (debit/credit), posting, hold, capture, release, reversal,
escrow, voucher, receipt, device, counter, sync, settlement, event time,
recorded time, daily close, invariant, ledger receipt (signed proof that the
ledger committed an entry; see §7.2).

## 2. Invariants (the contract — everything else serves these)

The invariants are catalogued in [invariants.md](invariants.md): 26

## 3. Data model

The pure types live in `crates/core`. Storage (step 1.08) follows them.

### 3.1 Identifiers
- Accounts, entries, holds and clients have their own ID types: UUIDv7,
  generated by the ledger ([ADR-0006](adr/0006-uuidv7-identifiers.md)).
- Retries are matched by the client's idempotency key, not by ID
  ([ADR-0008](adr/0008-idempotency-in-posting-transaction.md)).

### 3.2 Amounts
- `Money`: a signed 64-bit count of the currency's minor units (santim for
  ETB) plus its ISO 4217 currency ([ADR-0005](adr/0005-money-as-i64-minor-units.md)).
- Line amounts are `PositiveAmount`: greater than zero. The side gives the
  direction, never the sign.
- No floats and no rounding in the core. Overflow is an error, never a wrap.

### 3.3 Chart of accounts
- A chart is data: a TOML file such as `charts/wallet-provider.toml`,
  validated when loaded. See the
  [accounting model](accounting/chart-of-accounts.md).
- Each chart account has a four-digit code, a type (asset, liability,
  equity, revenue, expense), a kind (control or system) and a status
  (active or reserved). Control accounts are posted to only through
  sub-accounts such as `2010:cust-abebe`.

### 3.4 Account
- Opened from a chart reference, so its type, normal side and
  `allow_negative` always come from the chart.
- Fields: id, code, sub-account, name, type, currency, status,
  `allow_negative`, `debits_total`, `credits_total`.
- Status: open ⇄ frozen → closed. Only open accounts accept postings.
  Closing needs a zero balance; a closed account never reopens.
- Balance on the normal side: debits − credits for assets and expenses,
  credits − debits for the rest.

### 3.5 Journal entry
- An `EntryDraft` is a request: two or more lines (account, side, amount),
  optional metadata and an optional `event_time`.
- A `BalancedEntry` is an entry that passed every posting rule (§4.1). It can
  only be created by `validate` ([ADR-0003](adr/0003-multi-line-journal-entries.md)).
- After posting (step 1.09), the stored entry also has an ID, the client's
  idempotency key, `recorded_time` and its place in the hash chain (§7.1).

### 3.6 Time
- `recorded_time`: assigned by the ledger, strictly monotonic. Authoritative.
- `event_time`: claimed by the client/device. Informational, bounded and
  validated, never used for ordering.
- Both are microseconds since the Unix epoch, passed into the core, never
  read from a clock inside it.

## 4. Posting semantics

- **4.1 Validation.** Rules are checked in a fixed order, each with a stable
  numeric code (`crates/core/src/error.rs`): too few lines (1001), too many
  lines (1002), metadata too large (1003), amount not positive (1004),
  account not found (1005), account not open (1006), currency mismatch
  (1007), duplicate line (1008), amount overflow (1009), unbalanced (1010),
  account total overflow (1011), insufficient funds (1012, INV-8). Codes
  are never renumbered.
- **4.2 Posting.** One entry posts in one database transaction, all lines or
  none (step 1.09).
- **4.3 Holds.** A hold is a posting into its own held sub-account, then
  exactly one of: a capture (full or partial, the remainder returned in the
  same entry), a release, or an expiry once `expires_at` has passed
  ([ADR-0004](adr/0004-holds-as-postings.md), step 1.14, INV-16 to INV-18).
  Only the hold's own entries may post to its held account. An expiry
  worker expires due holds, skipping any being captured or released, and
  can be stopped and restarted at any point
  ([db-schema.md](db-schema.md#holds)).
- **4.4 Corrections.** History is never edited (INV-9).
  - A **reversal** is a new entry that mirrors the original exactly, at most
    once, never itself reversed (INV-14). It carries a reversal reason
    (such as `booking_error`) and its requester. A reversal that would take
    an account below zero is refused ([ADR-0013](adr/0013-reversals-never-overdraw.md)).
  - An **adjustment** is a manual correction or compensation, such as E14's
    goodwill credit. It carries an adjustment reason (such as
    `goodwill_credit`), a requester and a **different** approver (INV-25).
  - Both rules are enforced by the engine and again by the database.
- **4.5 Idempotency.** Every write carries a client idempotency key. The
  same key with the same request (same SHA-256 fingerprint) returns the
  original entry; the same key with a different request is refused with
  `IdempotencyKeyReused`. A refused posting does not use up its key. A
  client that lost a response can look up the entry by its key
  ([db-schema.md](db-schema.md#idempotency-and-retention), INV-13).

## 5. Offline sync

### 5.1 Threat model
Cloned device, replayed receipt, forged receipt, device that never syncs,
wrong/hostile clock, payer–merchant collusion, lost device, partial sync,
merchant uploads receipt twice, payer and payee upload the same receipt.

### 5.2 Device trust tiers
- Tier A: secure element (card). Tier B: hardware keystore (StrongBox/TEE).
  Tier C: software keys. Each tier has its own offline limit and expiry.

### 5.3 Voucher (offline allowance)
- Issued online. Posts an entry from the user's wallet to a per-voucher
  escrow sub-account (`2050:vch-…`, E16).
- Contents: voucher_id, device_id, account_id, amount (with currency),
  counter_start, expires_at, issuer signature.

### 5.4 Receipt
- Contents: device_id, voucher_id, counter, prev_receipt_hash, payee account,
  amount, event_time, payer device signature, optional payee ack signature.
- Hash chain per device: each receipt commits to the previous one.

### 5.5 Ingestion and settlement rules
- Outcomes: SETTLED, DUPLICATE, WAITING_FOR_GAP, CONFLICT, EXPIRED,
  OVER_LIMIT, BAD_SIGNATURE, UNKNOWN_DEVICE.
- Either party may upload; the result is identical regardless of who or when.
- Gap handling: how long to wait, what is settled meanwhile.
- Conflict handling: freeze device, settle nothing further, raise alert.

### 5.6 Voucher end-of-life
- Expiry, top-up, revocation, return of unspent escrow, late receipts after
  return (who absorbs the loss — policy hook for the client).

### 5.7 v1 rule
- Funds received offline are not spendable offline until synced
  (chain depth = 1).

## 6. Periods and daily close

- Close a period: freeze balances, compute and sign a journal hash.
- Late-arriving offline receipts post into the current open period with a
  reference to their event_time.

## 7. Audit and tamper evidence

### 7.1 Journal integrity
- Hash chain over the journal of entries.
- Signed checkpoints at each close; verification tool.
- Database role permissions: no UPDATE/DELETE on journal tables.

### 7.2 Ledger receipts (signed proof for every entry)

Offline payments already carry device-signed receipts (§5.4). Ledger receipts
extend signed proof to **every** committed entry, online or offline: the
ledger signs what it recorded, and the client keeps a copy it can verify
without trusting the database. Accounting stays double-entry; the receipt is
evidence, not a third ledger column.

- **When issued:** for every committed entry: payments, hold captures and
  releases, reversals, and settlement of an offline receipt. Failed postings
  get no receipt.
- **Contents:** receipt format version, the entry's canonical fields
  (§3.5), `recorded_time`, the entry's journal hash and `prev_hash`
  (§7.1), the signing key ID, and the signature.
- **Signature:** over a canonical, versioned byte encoding of the contents.
  Algorithm provisionally Ed25519; the algorithm and the encoding are decided
  in an ADR and are part of the public API once frozen.
- **Delivery:** returned with each successfully posted entry, and
  retrievable later by entry ID.
- **Idempotency:** the receipt is stored with the entry when the transaction
  commits. A retry with the same ID and body returns the stored receipt, never
  a newly signed one (INV-13).
- **Purity:** `mezgeb-core` stays free of keys and I/O. It returns the
  canonical bytes to sign; signing happens in the server/storage layer inside
  the same database transaction.
- **What it proves:** the ledger committed exactly this entry at this
  position in the journal. Combined with a signed checkpoint (§7.1), anyone
  holding receipts can detect a journal that was rewritten or had entries
  removed.
- **What it does not prove:** that the account holder authorised the
  entry. That needs client-signed requests (see §14).
- **Verification:** a standalone verifier (CLI and library) checks receipt
  signatures, key validity at `recorded_time`, and chain links against a
  checkpoint.

## 8. Storage (PostgreSQL)

- Schema v1, its constraints and roles: [db-schema.md](db-schema.md). The
  database enforces INV-1, 3, 4, 8, 9, 13, 14 and 24 on its own, as a
  second line of defence behind `crates/core`.
- Isolation level and lock ordering; deadlock avoidance
  ([ADR-0007](adr/0007-read-committed-ordered-row-locks.md), step 1.10).
- Indexes and partitioning (journal lines by month): steps 3.02, 3.04.
- Hot accounts: contention strategy (step 3.03).
- Migrations policy: `up` and `down` files, tested up → down → up; once
  applied outside development, never edited (a change is a new migration).

## 9. API

- REST over HTTPS with JSON, built with Axum
  ([ADR-0009](adr/0009-rest-api-with-axum.md)). Versioned in the path
  (`/v1/...`) and described by an OpenAPI document.
- Resources: accounts, entries (post, look up, reverse), holds (create,
  capture, release), account history, offline vouchers and receipts,
  periods (close). Designed in step 2.06.
- Every write takes an `Idempotency-Key` header
  ([ADR-0008](adr/0008-idempotency-in-posting-transaction.md)).
- Amounts are decimal strings with an explicit currency
  (`{"amount": "39.20", "currency": "ETB"}`), converted to minor units at the
  boundary ([ADR-0005](adr/0005-money-as-i64-minor-units.md)).
- Batch writes: to be decided in step 2.06.
- Every successfully posted entry includes its ledger receipt (§7.2).
- Errors: RFC 9457 Problem Details with stable, enumerated codes.
- Versioning and backward-compatibility policy.

## 10. Testing and verification

- Unit and property-based tests for every invariant.
- Deterministic simulator (`mezgeb-sim`): seeded, reproducible; injects
  crashes, retries, reordering, duplicate and delayed sync, cloned devices,
  clock skew. Checks all invariants after every step.
  - v1 (step 1.15): random postings, reversals, adjustments and holds, in
    independent lanes, on the reference ledger and on PostgreSQL. A share
    of attempts fails at a fault point and is retried with the same key.
    Every answer, account, hold and entry count must match the reference
    ledger, and verify must be clean.
- Fault points (step 1.15, test builds only): before lock, after lines,
  before commit, after commit (a lost response). A retry with the same
  idempotency key must leave exactly one entry.
- Chaos run (`scripts/chaos.sh`): PostgreSQL killed with SIGKILL under
  load, restarted and checked. Every acknowledged request exists once,
  every unknown one exists once or not at all, and verify is clean.
- Replay test: rebuild balances from journal and compare.
- Shadow mode: run beside an existing ledger and compare nightly.

## 11. Performance targets

- Entries per second (single node), p99 latency, hot-account throughput.
- Benchmark harness and reference hardware.

## 12. Operations

- Backups and point-in-time recovery, monitoring, alerts on invariant
  breaches, key management for voucher signing, disaster recovery.

## 13. Security

- Key hierarchy (issuer keys, receipt-signing keys, device keys), rotation,
  revocation list. Retired receipt keys stay published so old receipts remain
  verifiable.
- Authentication between client apps and the ledger.

## 14. Open questions

- Regulator requirements for offline stored value (limits, expiry, reporting).
- Who bears loss for late receipts after voucher return?
- Partial settlement when a gap never fills?
- Multi-currency in v1 or later?
- Client-signed posting requests (proof of authorisation): v1 or later, and
  is the signature stored with the entry?
- Receipt-signing keys in an HSM/KMS, or in process for v1?
