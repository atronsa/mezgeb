## Testing requirements

### Every fault point: one entry, and a clean verify

`tests/faults.rs` runs 11 writes at each of the 4 points, 44 cases:

- a payment
- an adjustment
- a reversal
- four hold placements
- a capture
- a release
- an expiry
- the expiry worker

Each write fails once at the point, then is retried with the same
idempotency key and a fresh entry ID, as a client would. After each:

- a crash before commit left nothing written; a lost response after commit
  left everything written
- exactly one entry exists for the key
- balances show the request took effect once
- a full verification is clean

### PostgreSQL killed 20 times under load

`scripts/chaos.sh` with its defaults: 20 cycles, 8 workers sending
transfers between 10 wallets for 10 seconds per cycle. In each cycle
PostgreSQL is killed with SIGKILL at a random moment between 2 and 8
seconds. There is no shutdown and no checkpoint, so the next start recovers
from the WAL.

The client logs every request before sending it and every answer when it
arrives. After the restart, `chaos_load check` compares that log with the
journal:

- every **acknowledged** request has exactly its entry
- every **rejected** request has none
- every request with an **unknown** outcome (sent, but the answer was lost
  in the crash) has one entry or none. It is then retried with the same
  key, as a client would: if it had committed, the retry returns the
  original entry; if not, the retry posts it once
- money is conserved: the wallets' total is unchanged

Then `mezgeb-cli verify --full` checks the whole ledger.

## The simulator

`mezgeb-sim` runs a random workload, the same for a given seed:

- **Operations:** deposits, transfers, adjustments, reversals, and holds
  (place, capture, release, expire), plus time passing
- **Lanes:** the work is split into independent lanes, each with its own
  accounts, client, clock, random numbers and reference ledger. Lanes share
  nothing, so they run at the same time on one database, and each
  operation still has exactly one right answer.
- **On PostgreSQL:** every operation goes through the engine and through
  the reference ledger (`MemLedger`), and the two answers must be identical,
  including refusals and their reasons.
- **Faults:** with `--faults N`, N in 1,000 attempts fail at a random
  `FaultPoint`. Each failed attempt is retried with the same key until one
  runs without a fault, and that answer must match the reference ledger's.
- **Checks during the run:** the reference ledger's invariant checker runs
  every 2,000 operations in each lane.
- **Checks at the end:** every account and every hold is compared, and so
  is each lane's entry count, and then a full verification must be clean.

A failure prints its seed, and running that seed again repeats the same
run.

## Acceptance criteria

**Zero invariant violations across 20 kill cycles and 1M simulated
operations.**

**20 kill cycles:** 0 violations, and verify was clean after every restart.
See the table above.

**1M simulated operations on PostgreSQL with faults.** A single run of a
million operations ran out of memory on this machine at about 535,000,
because the 32 reference ledgers grow with the run. That was not a ledger
error, and the database it left behind verified clean (1,070,436 lines).
The million was therefore run as **10 runs of 100,000 operations**, each
with its own seed and its own database. Every run used 32 lanes with faults
on 10% of attempts.

## Found along the way

- **A one-connection pool deadlocked the chaos setup.** `chaos_load setup`
  held its only connection while opening accounts, which needs a
  connection of its own. It now opens the accounts first.
- **The simulator's reference ledgers grow with the run.** A million
  operations in one PostgreSQL run needs more memory than this machine
  had, so the million was split into ten runs. A later simulator can trim
  what each lane keeps.
- **Cargo merges features across the workspace.** Building the whole
  workspace together turns on the engine's `test-hooks` for every crate,
  because the simulator needs it. A release build of `mezgeb-cli` must be
  built on its own (`cargo build -p mezgeb-cli`).
