## Implementation tasks

| Task | Done |
|---|---|
| Idempotency record in the same transaction as the entry (client, key, request hash, entry, response, created_at) | Yes. The response is the entry itself, rebuilt on a repeat: entries are immutable (INV-9), so it is always identical and no copy can drift. |
| Canonical request serialisation for the hash | Yes: a versioned, length-prefixed encoding of every field the client controls; SHA-256. The entry ID is excluded, because a retry may carry a new one. |
| Concurrent same-key requests: the second waits on the unique index, then returns the stored result | Yes: the key is claimed first with `INSERT … ON CONFLICT DO NOTHING`, before any account is locked |
| Same key, different hash: `IDEMPOTENCY_KEY_REUSED` | Yes: `LedgerError::IdempotencyKeyReused`, and nothing is written |
| `lookup_by_idempotency_key` | Yes |
| Retention policy, documented | Records are kept as long as their entry (forever); see [db-schema.md](../db-schema.md#idempotency-and-retention) |

A refused posting rolls back its claim, so it does not use up its key: once
the wallet is funded, the same request succeeds. Reversals are idempotent
the same way.

| The same key with a different amount gives an error and no entry | `a_reused_key_with_a_different_request_is_refused` | Pass |
| Abort after commit, before the response; retry returns the original, no new entry | `a_retry_after_a_lost_response_returns_the_original` | Pass: the connection the response was lost on is closed, the retry on a new connection returns the original entry, entries added: 1 |

Also: keys are scoped to their client; reversals are idempotent; a refused
posting does not use up its key; records are append-only (`42501` for the
service, `MZ001` even for the owner). Each test sends every attempt with a
new entry ID, as a real retry would. The fingerprint has unit tests showing
that every field changes it and that metadata boundaries are unambiguous.

## Acceptance criteria

**None of the tests can produce a duplicate entry.** Every test counts the
entries before and after; every repeat, concurrent or not, added exactly one.
**Pass.**

## Exit gate

**Gate:** a crash-after-commit retry is demonstrated in a recorded test run.

Demonstrated twice: with the test hook above, and with a real process
crash. `lost_response post-and-hang` posts a deposit, commits, and then
waits forever before answering; it is killed with `SIGKILL`. Two new
processes then retry the same request with the same key:

```
--- process 1: post-and-hang (SIGKILL after 5 s) ---
Killed                     timeout -s KILL 5 $L post-and-hang "$URL" "$KEY"
exit status: 137
--- process 2: retry with the same key ---
entries with key "demo-1794485840" before the retry: 1
this attempt's new entry ID:  00000000-0000-7000-8000-60134b754a02
entry returned by the retry:  00000000-0000-7000-8000-60134b26aeb2
entries with key "demo-1794485840" after the retry:  1
--- process 3: retry again ---
entries with key "demo-1794485840" before the retry: 1
this attempt's new entry ID:  00000000-0000-7000-8000-60134b77cc8e
entry returned by the retry:  00000000-0000-7000-8000-60134b26aeb2
entries with key "demo-1794485840" after the retry:  1
```

The first process committed and died without answering. Each retry came
with a new entry ID, got back the original entry, and posted nothing.
**Result: passed.**
