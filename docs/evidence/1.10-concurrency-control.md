## Acceptance criteria

**The tests pass 50 consecutive runs.**

The first attempt failed on its first run, and not because of locking: the
1,000-task tests queued for 20 pool connections longer than SQLx's default
30-second acquire timeout while all tests shared one slow database. Two
fixes:

- the test pools wait up to ten minutes for a connection (the tests measure
  locking, not queueing on a slow machine);
- the engine now reports a pool timeout as `Busy` (retry later) instead of a
  generic storage error.

Then, with the release build:

```
for i in 1..50: cargo test --release -p mezgeb-engine --test concurrency
consecutive passes: 50/50 in 2243s
```

**Pass.**

## Measured, not yet guaranteed: INV-12

INV-12 says `recorded_time` strictly increases in posting order.
`recorded_time_against_sequence` posts 1,000 entries in parallel and found
**no tie and no inversion** against `sequence`. That is an observation, not
a guarantee: `sequence` and `recorded_time` are taken by concurrent inserts,
and commit order can differ from sequence order. The guarantee comes with the
hash chain (step 2.09), which needs a single commit order anyway. The test
reports and does not assert, because asserting on a rare timing event would
be a flaky test. The schedule in the [invariant catalogue](../invariants.md)
and [db-schema.md](../db-schema.md) was updated.

## Exit gate

**Gate:** explain, from the PostgreSQL documentation, why the scheme
prevents lost updates.

Sources: PostgreSQL 18 §13.2.1 (Read Committed Isolation Level) and §13.3.2
(Row-Level Locks). The answers were written after reading a plain-language
explanation of the same five points, and are recorded as given:

| # | Question | Answer |
|---|---|---|
| 1 | What is a lost update? (a wallet of 100, two payments of 80) | Two payments read 100 at the same time. Both think "enough" and both spend. The wallet ends at −60, or one payment erases the other. Nobody saw the other's change. |
| 2 | What happens to the second payment's `SELECT … FOR NO KEY UPDATE`? | The lock holds the wallet row. The second payment must wait until the first commits or rolls back. Only one payment works on that wallet at a time. |
| 3 | What balance does it see after the first commits, and why is that enough? | After waiting, Read Committed gives it the newest committed row, not the old one. It sees 20. The check says 20 < 80, so it is refused. The check runs on the real current balance, and the lock keeps anyone from changing it. |
| 4 | Why lock in ascending ID order? | X locks A then wants B; Y locks B then wants A: both wait forever (deadlock). If everyone locks the lowest ID first, both queue for A first, so no circular wait is possible. |
| 5 | In "RC, no locks", what stopped the overdraft, and why is that not enough? | Without the lock, Rust read a stale balance and let the payment through; only `accounts_not_negative` stopped it. That is a backup, not a plan: it covers only the no-negative rule, and other rules (refund limits, escrow caps) have no database check behind them. |

**Result: passed.** Each answer names the right mechanism: the row lock
serialises payments per account, Read Committed re-reads the newest
committed row after the wait, the fixed lock order rules out deadlock
cycles (measured: zero deadlocks), and the database CHECK is a backstop for
one rule only.
