### The benchmark repeated 3 times with variance under 10%

Each scenario ran 3 times, interleaved with the others. The spread is
`(max − min) / mean` of the three runs' throughput, stricter than the
standard deviation.

| Scenario | Runs (postings/s) | Spread |
|---|---|---:|
| 2-line, uniform accounts | 710, 696, 704 | **2.1%** |
| 4-line, uniform accounts | 516, 524, 497 | **5.3%** |
| 2-line, one hot account | 297, 302, 287 | **5.1%** |
| 4-line, one hot account | 220, 223, 219 | **1.6%** |

**Pass:** every spread is under 10%.

**Why GitHub Actions, not this PC.** On Docker Desktop on Windows, a disk
sync took from 5 ms to 35 ms from one minute to the next (`pg_test_fsync`
run six times). Every commit waits for one, so runs there differed by
25–80%. On the GitHub runner a sync takes 0.08 ms, and the runs agree.

**Runners differ.** GitHub does not always give the same CPU. Earlier runs
of the same code got an EPYC 9V45 or 9V74, and posted 1.4–2× faster on
uniform accounts. Statements unaffected by any change, such as the line
insert, were slower by the same factor. A comparison with this baseline
must therefore use the same runner model, recorded in the run's summary.

## Baseline benchmark

`mezgeb-bench` through the engine, as it ships (without `test-hooks`).
Each run uses a fresh database with 1,000 wallets, and 16 connections
posting at once in a closed loop (each posts again as soon as its last
posting returns), measured for 60 s after 5 s of warm-up. Every run ended
with a clean full verification. There were no deadlocks or retries.
Workflow run 43488208349, 2026-11-13.

| Scenario | Postings/s | p50 | p99 | p99.9 | Max | Refused `Busy` |
|---|---:|---:|---:|---:|---:|---:|
| 2-line, uniform accounts | **704** | 22.6 ms | 41.2 ms | 54.0 ms | 88 ms | 0 |
| 4-line, uniform accounts | **513** | 30.1 ms | 66.8 ms | 87.1 ms | 121 ms | 0 |
| 2-line, one hot account | **295** | 10.5 ms | 638 ms | 4,127 ms | 4,985 ms | 171 (about 0.3%) |
| 4-line, one hot account | **220** | 13.9 ms | 609 ms | 4,026 ms | 5,000 ms | 257 (about 0.6%) |

Latencies are means over the three runs; Max is the highest of the three.
There is no target yet: this is the baseline that Phase 3 (step 3.01)
measures against.

**Where the time goes** (`pg_stat_statements`, one 10 s run per scenario):

- **Uniform accounts:** the line insert is the costliest statement (2.2 ms
  for 2 lines, 3.7 ms for 4), then the account updates. The deferred
  balance check runs once per row, 3 times for a 2-line entry and 5 times
  for a 4-line one. See
  [db-schema.md](../db-schema.md#what-one-posting-costs).
- **Hot account:** the lock `SELECT` averages 40–45 ms, almost all of it
  queueing for the one row. The rest of the posting takes under 2 ms.

**The hot account's tail.** The queue for one row is not fair. The median
posting waited about 10 ms, but one in a thousand waited about 4 s, and a
few reached the 5 s lock timeout and were refused with `Busy`. That is the
engine's designed answer: the posting writes nothing, and the client
retries. The benchmark now reports `Busy` as a rate and fails only on other
errors. In run 43488208349 it still counted them as errors, which is why
that run's summary says FAIL. Splitting hot accounts is step 3.03.

**Coordinated omission.** In a closed loop, a slow posting delays the
worker's next one, so the latencies are those of a saturated system, not
of clients arriving at their own pace. `mezgeb-bench --rate N` runs an
open loop instead, measuring each latency from when the posting was due.
The baseline above is closed loop.

## Found: the lock timeout did not bound the wait

`PostOptions::lock_timeout` (5 s) was documented as the longest a posting
waits for its accounts. PostgreSQL, however, applies `lock_timeout` to each
lock wait separately. On a hot account, one `SELECT … FOR NO KEY UPDATE`
can wait several times in a row: first behind another waiter, then behind
that waiter's transaction.

In the first 60 s run on GitHub, the slowest postings waited up to 29 s.
Some reached the `mezgeb_app` role's 30 s `transaction_timeout`, which
closes the session. Each was refused with `Busy` and wrote nothing, and
every verification was clean, so no money was wrong. But clients waited six
times longer than promised and lost their connections. The benchmark then
failed millions of postings in a row, because each worker kept its one
connection for the whole run.

**Fix (#42).**

- Each write's transaction also sets `statement_timeout` to the same value,
  in the same round trip, so a whole statement is bounded. A cancellation
  (`57014`) is `Busy`.
- `the_lock_timeout_bounds_the_whole_wait` makes a posting wait twice,
  200 ms and then 300 ms, with a 400 ms timeout. Before the fix it posted
  after 633 ms; after it, the posting is refused with `Busy` at 400 ms.
- The benchmark takes a pooled connection per posting, as a service does.

In the baseline after the fix, the longest posting took 5.000 s, and no
session was closed.

## Phase 1 review

**What Phase 1 built.** A posting engine on PostgreSQL that:

- posts any balanced multi-line entry, atomically
- keeps running totals that verification proves against the lines
- refuses overdrafts under concurrency
- applies each idempotency key once, through crashes and lost responses
- reverses and adjusts without changing history
- holds money in two phases, with expiry

A reference ledger (`MemLedger`) gives the right answer to every
operation, and the property tests, the differential test and the
simulator compare the engine with it.

**Known limits, and the step that addresses each:**

| Limit | Step |
|---|---|
| One hot account handles about 300 postings/s on this runner. Its lock queue is unfair: about 0.3–0.6% of postings wait out the 5 s timeout | 3.03 (hot accounts) |
| The deferred balance check runs once per row instead of once per entry | 3.01 (performance) |
| Benchmark numbers depend on the runner's CPU, which GitHub varies | 3.01 (reference hardware) |
| The simulator's reference ledgers grow with the run, so a million operations on PostgreSQL ran as ten runs of 100,000 | 2.14 (simulator v2) |
| Building the whole workspace turns on the engine's `test-hooks` for every crate (Cargo merges features). The service must be built on its own (`cargo build -p mezgeb-cli`) | 3.11 (deployment) |
| No API, periods, hash chain or receipts yet (INV-10, INV-11, INV-26) | 2.05–2.09 |
